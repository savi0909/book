**Rolling window: `MovieScheduleMaintainer`**

> Correction (2026-10-08 review): the maintainer is enabled on **both** APIs, not
> api-a only. `MOVIE_SCHEDULE_ENABLED` sits in the `&api-env` anchor, which api-b
> merges (`compose.yml`), and `docker inspect` shows it on both containers. The
> per-batch advisory lock decides which replica does each batch. The hold keys
> are `mv:<run>:<i>:h1` / `:h2` and `mv:<run>:<i>:pay` (`MovieRunService.journey`).
- Runs on its own daemon executor, gated by `movie.schedule-enabled`. It is on in
  base Compose (api-a only) and off in tests and `compose.movie.yml`.
- Every tick runs purgePast and then fillWindow, under
  `pg_try_advisory_xact_lock(0x4d6f766965)`, so only one replica does the work.
- Fill is a single set-based CTE: `generate_series` slots between 09:00 and the
  last start at 23:30, with 20 min turnaround. A NOT EXISTS check per screen-day
  plus ON CONFLICT DO NOTHING make it idempotent, and seats are inserted in the
  same statement.
- Purge deletes whole past local days in one statement: receipts → payments →
  audit → booking_seats → show_seats → bookings → shows. NO ACTION FKs are
  checked at statement end, so the bookings↔payments cycle is fine. Shows with
  PENDING/RETRY_PENDING payments are kept, and each purge is recorded in
  `movie_purge_log`.
- **JIT incident:** generate_series row estimates pushed plans over
  jit_above_cost, costing about 733 ms of JIT per no-op batch versus 8.4 ms
  without it. This kept PostgreSQL at 100% CPU. The fix is `SET LOCAL jit = off`
  inside `locked()`.
  - First hypothesis (autovacuum) was wrong.
  - First "fixed" claim was wrong: the deployed jar was stale, because mvn test
    does not repackage. This makes a good debugging case study.
- First live fill produced 40,333 shows and 14,254,490 seats in 467.8 s. The
  audit found 0 seat mismatches, 0 overlaps and 0 past shows.
